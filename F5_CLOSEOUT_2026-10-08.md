# F5 CLOSEOUT — 2026-10-08

## The original problem

Gating decisions in Genesis hinged on a `confirmed: boolean` carried in
`ActionPlan.parameters`. Any caller — agent, adapter, planner, or a
prompt-injected string — could set `confirmed=True` and satisfy the
executor gate. The flag carried no evidence of a human decision, no
binding to what was actually being approved, and no proof it came from a
trusted channel. Attack A6 in the adversarial battery is the minimal
reproduction: a plan with `confirmed=True` and nothing else.

## What replaces it

Four mechanisms that together form one system. None is sufficient alone.

1. **Blast-radius tiers over 143 registered capabilities.** Every
   capability carries an explicit `BlastRadius` and a non-empty
   `blast_radius_reason`. Six dynamic evaluators refine the static tier
   per call. Any capability lacking a classification falls back to
   deny-by-default rather than inheriting a permissive default.
   `BlastRadius` — not `risk_level` — is the single source of truth.
2. **`AuthorizationGrant`** — a structurally un-forgeable token that
   binds `(operation, hashed arguments, minted approval id)`. It travels
   on the trusted adapter channel and cannot be supplied through plan
   parameters. A grant authorises a *specific* plan: if the plan carries
   a second, uncovered path, the grant is refused.
3. **Schema hardening** — `AgentFrameworkAdapter` injects
   `additionalProperties=False` centrally, so undeclared fields
   (including `confirmed`) raise `TypeError` at the boundary rather than
   reaching the executor.
4. **Workspace boundary with fail-closed handling** — any capability
   whose target resolves outside `GENESIS_WORKSPACE_ROOT` escalates to
   Tier 1 (`irreversible_or_outward`), including *reads*.

## The workspace root decision

Deliberately **not** `backend\` — that directory holds `.env`, the sealed
corpora, and the safety code itself. Deliberately **not** system temp —
writable by other processes, and temp paths have proven to produce
ordering-dependent failures on this host. A scratch root is the only
choice where self-protection is provable.

## Step 3: the `confirmed` stand-in - traced, then replaced

### Entry-point trace

`ActionPlan._validate_operation` rejects any operation that is neither in
the registry nor in `KNOWN_DENIED_OPERATIONS`. `KNOWN_DENIED_OPERATIONS`
is the escape hatch that lets a plan be *constructed* for an operation
with no registered capability. Of those eight, six have **no registry
entry at all**:

| operation | in registry | risk requires confirmation | blast radius |
|---|---|---|---|
| `filesystem.delete` | no | yes | irreversible_or_outward |
| `filesystem.move` | no | yes | irreversible_or_outward |
| `filesystem.rename` | no | yes | irreversible_or_outward |
| `process.kill` | no | yes | irreversible_or_outward |
| `shell.execute` | no | yes | irreversible_or_outward |
| `system.sleep` | no | yes | irreversible_or_outward |
| `system.restart` | yes | no | irreversible_or_outward (unavailable) |
| `system.shutdown` | yes | no | irreversible_or_outward (unavailable) |

This is why the stand-in could not simply be deleted: the adapter
promotes a valid approval token to `confirmed=True`, so with the flag
alone as the gate, `shell.execute` would have become grantable.

### The replacement

`action_executor.py` no longer reads `confirmed` for any decision. It
consults `KNOWN_DENIED_OPERATIONS` directly, so an explicitly denied
operation cannot be enabled by a flag **or** by a grant. That is
strictly stronger than the stand-in it replaces.

`genesis.py:_execute_pending_action` no longer reads capability metadata
to inject `parameters["confirmed"] = True`, and no longer prints
"Confirmed action approved by user." It records the user's yes as
`source`, then says honestly that grant-gated operations remain
blocked because no approval channel exists yet.

Note: these operations are in practice refused even earlier, by
`execution_safety`'s policy gate (`execution_stage == "safety"`). There
are now two independent denials; either alone is sufficient.

### Does any gating decision anywhere still read `confirmed`? - NO

- `action_executor.py:358` and `:845`: now comments describing the removal.
- The executor has **zero** functional reads of the flag.
- `action_executor.py:1780-1799` pass `confirmed=True` *down* to
  OSManager as post-authorization notification, not as a gate.
- `agent_framework_adapter.py:2592` injects `True` only after
  `is_valid_approval_token(...)` validates a real token, and mints the
  `AuthorizationGrant` alongside. Not a bypass.
- `agent_framework_adapter.py:2577` forwards a tool argument into plan
  parameters; `:4670` honours an existing token.

## The ordering blocker: mechanism verified, fixed

**The original explanation was wrong and was corrected by measurement.**
The claim that `Path` gets "permanently rebound to `PosixPath`" was
false: the import binds the same class object, and `Path(...)` chooses
per call. The decisive experiment:

```
os.name=nt     PosixPath() -> NotImplementedError
os.name=posix  PosixPath() -> NotImplementedError   <- guard is IMPORT-TIME
os.name=posix  Path(.)     -> PosixPath               <- factory IS live
```

`pathlib.Path` is a live factory that reads `os.name` on every call,
while the concrete classes are fixed at import. Chain:
`app_manager.inspect` -> `resolve_application_record:337` ->
`unified_discovery:209` -> `app_discovery:113` (called unconditionally)
-> `:319 Path(directory)` builds a `PosixPath` instance ->
`:329 .glob("*.exe")` -> `with_segments` -> `type(self)(...)` ->
`NotImplementedError`. It is **not** a deliberate raise.

The fix patches the narrow seam the code under test actually reads
(`_PosixOSView` replaces `app_mod.os` with a proxy reporting
`name="posix"`), so global `os.name` stays real and `Path` keeps
producing `WindowsPath`. No production change.

Four-way proof: alone 1 passed; in its file 12 passed; file in reverse
order 12 passed; preceded by each of 11 siblings **0/11 failures**.
Plus a `finally` assertion that `os.name == "nt"` and `Path` is not
`PosixPath`.

## Pollution sentinel

Autouse fixture snapshotting before each test and comparing after.

- **FAIL tier**: `os.name`, `sys.platform`, `os.sep`, `pathlib.Path`,
  and the `LLMIntentResolver` budget/timeout attributes. These are
  genuine test defects. Proven with a temporary mutation test that was
  caught by name with before/after values, then deleted.
- **RECORD tier**: `GENESIS_*` env keys. `ai/ai_engine.py:78` calls
  `load_dotenv()` inside `AIEngine.__init__`, so *any* test that builds
  the full runtime injects `.env` into `os.environ` for the life of the
  process. That is production behaviour, not a test bug.

The first sentinel version failed tests on the RECORD tier, and that was
**wrong**: it blamed whichever test happened to construct a runtime
first, which is arbitrary. It made the default ordering green and the
alternate ordering red, with six different files "at fault" across
runs. That is a false positive, not a defect.

Resolution: the suite is now hermetic by default - an autouse
`genesis_env_guard` restores the keys around every test, so the leak
cannot propagate and cannot make results order-dependent - while the
guard *records* which tests introduced them and a terminal summary
reports them. Nothing is hidden and nothing is falsely blamed. Fixing
this properly means moving config loading out of the constructor.

The sentinel also found a real defect in its own first version: failing
in teardown while `os.name == "posix"` left pytest unable to render its
own traceback (`INTERNALERROR`, whole session lost). It now restores
state *before* failing.

It also caught a leak that was **structurally invisible to the fast
gate**, because the affected tests are `live`-marked and deselected by
`-m "not live"`. That is a real gap in the fast-suite gate.

Runtime: unchanged within a few seconds on the fast suite.

## The approval flow - the next required piece (not built here)

This section is a **specification, not an implementation.** It is the
first follow-up because F5 is unusable without it: the boundary gates
every out-of-workspace operation, and today nothing can issue the grant
that would unblock one.

**Status: Phase 13 (Human Escalation) work pulled forward**, the same
way the Phase 11 bridge was labelled. It is called forward rather than
left to Phase 13 because activation makes it load-bearing today.

Required security properties:

1. **Only a human channel may approve.** The REPL's real stdin is the
   only approval channel. \ApprovalStore.approve()\ must not be
   reachable from any capability, tool call, model output, or any other
   model-influenced path. Approval is a human decision, never an
   inference.
2. **The prompt shows derived truth, not model text.** The operation
   and arguments shown must come from the hash-bound
   \AuthorizationGrant\ / canonical \ActionPlan\, never from a
   model-authored string. A model that describes an operation as
   harmless must not be able to render a prompt that looks harmless.
3. **Non-interactive context denies by default.** With no TTY (service,
   CI, piped stdin, GUI-launched process) approval is refused. There is
   no "assume yes" flag, no auto-approve default, and no environment
   variable that grants approval.
4. **Approvals are single-use.** One grant, one dispatch. Re-prompt for
   each new operation; never cache an approval across calls.
5. **Protected paths are visibly distinct.** Approvals for `.env`,
   credential stores, Genesis source, sealed corpora,
   `workspace_boundary.py`, and `authorization_grant.py` must be
   rendered in a visually different style, naming the protected class,
   so that approval does not become a reflexive click. (Overlaps with
   follow-up 5 below.)

Explicitly out of scope for the first version: batch approval,
"approve all in this directory", and any remembered-approval store.
Each is a new weakening surface and should be argued for separately.


## Residual follow-ups, in priority order

1. **The approval flow.** Nothing in the runtime can issue a grant, so
   under activation every out-of-workspace operation is unreachable in
   production, not merely gated. Specification is in this document
   above. This gates real usability of the feature.
2. **Generated-artifact defaults resolve into the workspace.** The
   Phase 0 bridge is currently gated because its relative target lands
   in `backend\`. This is why five test files needed retargeting.
3. **Two-axis refinement.** Ordinary reads outside the root should be
   free; reads of a named sensitive list (`.env`, credential stores,
   Genesis source and corpora) stay gated. Current strict-first
   behaviour is a decision, not an oversight.
4. **8.3 short names and symlinks are unverified on this host.**
5. **A human-approved grant can authorise edits to safety code** - by
   design, but approval prompts for protected paths should be visibly
   distinct so approval does not become reflexive (Phase 13).
6. **Test-suite speed.** Full suite is ~21 minutes. A medium tier is
   worth considering. Note the fast gate structurally cannot see
   `live`-marked tests, which is how a real leak hid from it.
7. **Move `load_dotenv()` out of `AIEngine.__init__`** so constructing an
   engine stops mutating process-global state.
8. Optional `risk_level` lint.
